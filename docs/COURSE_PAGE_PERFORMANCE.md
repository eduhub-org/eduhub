# Course Page Performance Notes

## Purpose

Issue
[#1681](https://github.com/eduhub-org/eduhub/issues/1681) started with the
Degree Participations tab, but the same data-loading pattern affects normal
course management pages. The main risk is loading large participant datasets
before the user opens the tab that needs them.

This document keeps the durable context for future performance work. It is not
an active implementation checklist.

## Current Approach

The course management page should keep the first render focused on page-shell
data: course metadata, header data, tab visibility, and access checks. Large
participant data should be loaded by the tab that owns it.

Implemented parts of that approach:

- Degree Participations uses dedicated paginated queries and the
  `DegreeParticipationStats` view.
- Applications uses a server-side `TableGrid` query with `limit`, `offset`,
  filters, ordering, and aggregate counts.
- Applications bulk email actions use a separate lazy recipient query so they
  do not require loading every application into the table.
- Manage-course loading states keep the header and tabs stable while tab data
  loads.

Remaining candidates for future work:

- Split the manage-course shell further if the initial `MANAGED_COURSE` payload
  becomes measurable again.
- Split Course Participations metadata from paged table rows. The table rows
  are paginated, but sessions, achievement options, and achievement records are
  still returned with the table query.
- Split normal course pages so `COURSE_WITH_ENROLLMENT` fetches only the
  current user's enrollment instead of all `CourseEnrollments`.
- Add database indexes only after measuring a slow query under the performance
  dataset.

## Performance Test Dataset

The large performance dataset is intentionally opt-in and is not loaded by
default `docker compose up`. This keeps normal local startup light while still
making slow course and degree pages reproducible.

Important files:

- Generator:
  `backend/seeds/utils/generate_performance_degree_seed.py`
- Generated SQL:
  `backend/seeds/performance/performance_degree_seed.sql`
- Loader:
  `backend/seeds/utils/load_performance_degree_seed.sh`

The checked-in dataset currently targets 5000 participants in a
`Performance Test Degree`, plus linked generated courses and events. It includes
realistic participation statuses and motivation ratings so Applications,
Participations, Degree Participations, and bulk email flows can be tested with
large row counts.

## Regenerating The Dataset

Run this from the repository root when the generator logic or target size
changes:

```bash
python3 backend/seeds/utils/generate_performance_degree_seed.py --users 5000
```

The default Machine Learning Degree seed is separate. It remains part of
`backend/seeds/default/initial_seeds.sql` and is generated by:

```bash
python3 backend/seeds/utils/generate_ml_degree_seed.py --users 300
```

## Loading The Dataset

Start the local Docker stack, then load the performance seed:

```bash
bash backend/seeds/utils/load_performance_degree_seed.sh
```

The loader executes `psql` inside the Hasura service and reads the SQL file from
the existing `./backend/seeds:/hasura-seeds` Docker volume. It uses
`HASURA_GRAPHQL_DATABASE_URL` from the container environment.

The default Docker Compose service name is `hasura`, and the default container
name is `eduhub-hasura`. If a local setup uses a different Compose service name,
override it:

```bash
HASURA_SERVICE=hasura bash backend/seeds/utils/load_performance_degree_seed.sh
```

## Validation Notes

Useful checks after loading the performance dataset:

- Open the Performance Test Degree on the manage course page and confirm the
  first tab renders before participant-heavy tabs are opened.
- Open Applications and Degree Participations and verify pagination, sorting,
  filtering, and loading states.
- Exercise Applications bulk email actions for status and rating groups. Large
  recipient groups should fall back to copying emails when the generated
  `mailto:` URL would exceed the configured limit.
- Watch GraphQL response sizes and browser memory in the local dev tools when
  switching tabs.

## Future Follow-Ups

- Measure `CourseParticipations` with the performance dataset and split static
  metadata from paged rows if it is still large.
- Replace normal course page all-enrollment loading with a viewer-specific
  enrollment query.
- Add focused tests around server-side `TableGrid` pagination, sorting, and
  filter variable generation.
- Inspect Hasura SQL for the slowest measured paths before adding indexes.
